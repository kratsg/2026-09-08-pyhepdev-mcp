One minute of level-setting, since this is an introduction for scientific software developers. MCP is an open protocol, originally from Anthropic, now with a public spec and SDKs everywhere: your assistant speaks JSON-RPC to a server you write, and that server wraps whatever you already have, the Rucio client, pyAMI, a workflow system. Three primitives, and honestly tools are the one that matters in practice: typed functions the model can call, described by a name, a schema, and a docstring. The pitch to this room: this is not prompt engineering and not training a custom model. It's ordinary interface design for an unusual caller. If you can write a Python API, you can write one of these; there's a minimal example below if we want it.

The point

The limiting factor is rarely the model. It's reliable, secure access to what scientists already use.

Start with the three-box diagram every MCP tutorial draws, because it's true: agent, server, backend, and the SDK makes that a weekend of work. Then reveal the second row: this is the same tool call as it actually runs in production. The user authenticated through Keycloak, the agent holds a personal access token, the gateway authenticates and authorizes once, a broker mints a short-lived identity token for exactly one backend, the backend redeems it for a real grid credential from a custodial service, and only then does Rucio hear about it. Every box in that second row exists because something broke without it. That's the talk in one line: design the interface for the model, design the architecture for the credential.

And the prose is part of the API

The model reproduces docstring examples verbatim. Doc bugs are behavior bugs: one release fixed query syntax in documentation four times in one day.

ami-mcp commit 901f339 "optimize MCP tools for LLM usefulness"; doc fixes 74e9063, 000160c, 78a2ce3, 8bea8de.
This is the first lesson chronologically. ami-mcp wraps a twenty-year-old metadata service. The naive wrapper worked, passed its mocked tests, and was unusable: a hundred fields, a fourteen-column tag table, duplicates. One commit, titled "optimize MCP tools for LLM usefulness," is basically a catalogue of raw-wrapper failure modes and their fixes: allowlist, pivot, dedup. And it found a real parsing bug the mocks had hidden, because the real CVMFS files use double tabs. Second half: AMI is the one server where we teach the model a query language instead of wrapping every command. That makes the documentation executable, and it had to be debugged like code, against the live service. Four same-day commits fixed syntax errors in docstrings.

  • Empty results route too

Honest gap

None of this sets the spec's isError flag. Do both.

Principle one of five. The consumer of an MCP is a probabilistic programmer: it course-corrects from prose, so an error message is not diagnostics, it's the next instruction. Three things to copy: return errors as normal results instead of raising, name the specific next tool in the recovery line, and give empty results a route too, because an empty result is the most common silent failure. And feed the same category taxonomy into your metrics: our Grafana can show which confusions agents actually hit. The honest gap: we return errors as plain text without the protocol's isError flag, and that bit us at the platform layer, where failing calls were audited as successes until we fixed it. Keep the recovery prose, and also set the flag.

Context is a bounded resource

Pagination theater

Five tools returned a tidy 100-row page while materializing everything upstream: one 500k-file container, downloaded to serve a page.

Fixed by an external contributor, 24f7497. Lazy end to end, or it doesn't count.

Every cap has three legs

  • Enforced server-side, and tested
  • Announced in-band: Pass `offset=50` to see more.
  • Recoverable: "narrow path and retry"

Worst case is a known number: 1 MiB · 200 matches · 10 s · 4 ops/user.

At the platform layer

The gateway forwards no backend instructions (one ships 10.5 KB): it composes its own 2–3 KB and filters the tool list per user.

Principle two: treat the context window as a metered resource with a budget, the way you treat memory. The war story: five of our tools looked perfectly paginated from the model's side while materializing everything upstream; a half-million-file container got downloaded to serve one page. An external contributor caught it. Lazy end to end or it doesn't count. The rule I'd put on a poster: every cap needs three legs. It has to be enforced server side, it has to announce itself in the output so truncation never silently distorts the model's world view, and it has to come with a recovery move. The one leg that rots is enforcement; we found a documented grep cap that was never actually clamped, so test the clamps. And the same principle recurses at the platform: don't forward every backend's instructions; own that channel and keep it small, and trim the tool list per user.

The principle

Make the dangerous parameter unrepresentable, not documented.

Principle three. Every agent-facing schema in the fleet has the same absence: there is no owner or username parameter anywhere. The user is whoever the verified token says, full stop. What makes this a real pattern rather than a slogan is that five servers implement it with completely different mechanisms: Kubernetes owner labels for notebooks, an actual setuid subprocess for the filesystem so the kernel is the enforcement, and the VOMS nickname inside the redeemed proxy for Rucio and AMI. And one platform-level sharpening: even the token doesn't carry authority. Groups and permissions are resolved live from the identity directory on every call, never read from token claims, so removing someone from a group takes effect in seconds, not at token expiry.

Keep credentials out of the MCP

Lifetime == one call

Redeem → 0600 file → one call → delete. No standing secret; the deletion is tested.

Exchange, never forward

The user's token never goes downstream (a spec MUST). Re-mint per hop: aud= one service, 600 s, no authz claims.

Custodians per secret

Passphrase, password, pool key: each in its own tiny service, fenced to one caller.

"Authorization model: none beyond identity, by design. … Do not add capability logic here based on token claims." the same module docstring in all three token services (krb5 app.py:1–10); authorize once, upstream

Needing credentials does not make the MCP the place to mint or store them.

The architectural heart, and the abstract's promise: authentication without exposing user credentials. Three moves. First, credential lifetime equals tool-call lifetime: the MCP redeems a credential for this caller, uses it for exactly one backend operation, and deletes it on the way out; we test the deletion, not just the redeem. Second, exchange instead of passing through: the platform never forwards the user's token, which the MCP spec itself forbids. We even rejected the SDK's convenience proxy class because its default forwards headers. What goes downstream is a broker-minted identity token good for one audience for ten minutes, and heavy material like proxy PEMs never transits the gateway at all: the backend redeems it directly from the broker. Third, the root secrets. The pool password can mint tokens for anyone; the Globus passphrase unlocks the user's grid identity. Each lives in its own tiny custodial service whose docstring literally forbids adding authorization logic. Authorize once, at the broker; custodians verify who is calling and nothing else. Deep-dive below if credential plumbing is your thing.

The custodians · deep-dive

voms-token-service

The only pod that sees home dirs and Globus passphrases. Runs voms-proxy-init impersonated; privilege floor found live, five times.

krb5-token-service

Password → kinit → ticket; zero secrets at rest, passwords zeroed on every exit path. Rate limiter protects CERN's lockout counter, not itself.

condor-token-service

Runs condor_token_create next to the pool key, which "must never reach the broker": it can mint any identity.

Why three services, not one

Different privilege floors (root+caps / none / one init container). Merging them forces the union of privileges onto everything. Each is a one-question audit: "did this call come from the broker?"

Orchestrate the hardened native binary; parse artifacts (ccache bytes, PEM), never CLI prose.
Deep-dive for questions. Three services because three root secrets with three different privilege needs. voms needs root plus capabilities to read user keys, and every one of those facts was discovered in production: grid tooling checks file ownership, not just mode. krb5 needs no privileges at all and holds nothing; its rate limiter exists to protect CERN's account-lockout counter, a third party, which is my favorite example of consequence-driven design. condor sits next to the symmetric pool key that can mint tokens for any identity, which is exactly why it must never reach the broker's trust domain. Common thread: all three shell out to the battle-tested native binary and parse artifacts, ccache bytes and PEM, never the human-readable CLI output, which turned out to be locale-dependent.

The environment is the hard part

A bridge you shouldn't need

CERN's OpenSearch MCP is SPNEGO-only; our world speaks broker JWTs. A ~600-line adapter, zero MCP awareness:

  • verify JWT, redeem a throwaway ccache
  • Kerberos = curl --negotiate, zero lines of Python
  • ccache deleted per request, tested

After green CI: six straight failures

  1. dependency packaging
  2. no krb5.conf in the container
  3. CERN Grid CA not in the Mozilla bundle
  4. NetworkPolicy blocking KDC port 88
  5. reverse-DNS SPN mismatch
  6. gzip body, Content-Encoding dropped

All environment, none logic.

The principle

Green CI cannot reach credential plumbing. Budget live verification; the manifest is part of the security design.

Principle five. One backend we genuinely could not change: CERN's OpenSearch MCP only speaks SPNEGO, negotiated Kerberos at the Apache layer. The answer was a deliberately dumb adapter: it translates authentication and nothing else, no JSON-RPC parsing, no policy, no standing secret. The entire Kerberos implementation is an environment variable and curl's GSSAPI. The right half is the real lesson. This service had full test coverage and green CI, and then failed six times in a row in production, once per layer of the environment: packaging, kerberos config, CA trust, network policy, reverse DNS, and a lossy header. Not one was a logic bug. The same story repeats across the credential services: secret mounts whose permissions the native binary refused, a chart whose own default network policy blocked its own default JWKS URL. Mocks can't reach any of that. Plan for it.

What breaks at ten MCPs (that one never sees)

  • Silent shadowing: same-name tools resolve by registration order; prefix everything
  • Registry ≠ wire contract: service name doubled as token audience; one rename 401'd the fleet
  • List-time credentials: a backend needing auth just to list tools is invisible
  • Version skew: new upstream tools ship disabled until mapped, opt-in per tool
  • A permission matrix: 12 permissions × 8 services × 124 tools
  • Failure isolation: a dead backend leaves tools/list, calls don't fail

The platform bar

The Nth MCP must be config, not code. And tool quality can't be fixed centrally: descriptions forward verbatim, so publish authoring conventions.

af-mcp-platform issues #113, #257, #121 · 289 commits, 77 days, 1,337 tests. ↓ more scars
Everything so far was about one server at a time. At ten, a different class of problem appears, and none of it is in the MCP spec. Quick tour: naming, because two backends will eventually serve the same tool name and the failure is silent shadowing, not an error. Identity of a service versus its wire contract: our worst outage was a rename, because the registry name doubled as the token audience; they're separate fields now with a do-not-change comment. List-time credentials: rucio needs auth just to enumerate tools, which made it invisible to aggregation. Version skew: backends deploy independently, so new tools are disabled until reviewed. And failure isolation: when OpenSearch is down, its tools simply aren't in the list. The bar we hold ourselves to: adding the tenth service is configuration, not code. That's the payoff of the whole architecture.

Invariants: the user's token is never forwarded · heavy credentials never transit the middle · every call audited.

This is the platform in one call, and it's the slide to slow down on. Walk the six steps. The thing to notice is how many different tokens exist: the personal access token the client holds, the ten-minute identity token the broker mints for exactly one backend, and the VOMS proxy the backend redeems directly from the broker. Each hop exchanges rather than forwards, which is exactly what the MCP spec's authorization section demands, and the proxy PEM never passes through the aggregator at all. Also notice what the identity token does not contain: any authorization claims. The docstring in the broker says if a backend is ever written to test token.permissions, the design has failed. Authority lives in one place. And the audit spine: exactly one record per call, success, failure, or denial, joinable to the client's trace and the usage accounting by one id.

Interfaces that travel

Across LLM providers

  • Design for the least-capable client: a cleaner scope-based design was written up, then deferred; only one client supports it
  • Standard OAuth, standard transports, no provider-specific hooks

Across experiments

  • rucio-mcp already serves ATLAS, CMS, DUNE, ESCAPE: the domain layer is VO-agnostic
  • Transplant the shape (broker + custodians + config-only services), not the CERN-specific code

↓ how our choices scored against the evolving MCP spec
The abstract's closing claim, made concrete. Across providers: the discipline is designing for the least-capable client. We had a genuinely cleaner design for routing based on OAuth scopes, fully written up, and we shelved it because only one client on the market supports the feature; the write-up is committed next to the code. Same story with the OAuth metadata fallback we deleted after a different client choked on it. Standard auth, standard transports, nothing provider-specific: that's what "works across providers" costs. Across experiments: rucio-mcp is already multi-VO because Rucio is, and the whole facility shape, broker, custodians, config-only services, transplants to any lab. What doesn't transplant is the CERN-specific plumbing, and that's fine: it's all behind one provider interface and per-service config. If you take one sentence home, take the abstract's: interoperable tool interfaces will matter more than model-specific integrations.

Backup scorecard, useful for the "is MCP stable enough to build on" question. Three of our production-driven choices were later standardized: statelessness, client-id metadata documents, and betting on tools as the durable primitive. The auth model is compliant with the spec's strictest MUSTs, including the token-passthrough prohibition, which our broker architecture essentially exists to satisfy. And two honest misses: we returned markdown only, no output schemas and no tool annotations, and the platform paid for both, a metering double-count bug and a hand-maintained read/write list. The correction is authoring conventions and a retrofit. If you start tomorrow, start with structured outputs.

When is an MCP server appropriate?

Build one when

  • a library or service scientists already use
  • assistants need it repeatedly, across clients
  • you can bound outputs and make errors recoverable

Skip it when

  • a one-off script would do
  • the backend has no stable contract
  • the "tool" would hand the model a credential

Close on the abstract's promise: when is an MCP server appropriate. Build one when there's an existing library or service with real users, when assistants will need it more than once and from more than one client, and when you can actually bound the outputs and make the errors recoverable, because those are the two properties the model experiences directly. Skip it when a script would do, when the backend has no stable contract to wrap, or when the honest implementation would hand the model a credential; fix that boundary first. Then the two closing lines, slowly: interoperable tool interfaces will matter more than model-specific integrations. The checklist below is the hallway version; the full dossier with commit-level citations is mcp-design-talk.md in the slides repo.

The checklist · backup

  • One domain, stated non-goals
  • Descriptions written for the model, tested live
  • Every output bounded; truncation announced
  • Errors name the next tool, and set isError
  • Structured outputs from day one
  • No username parameters, anywhere
  • No standing credentials: redeem per call, delete after
  • Authorize once, upstream
  • Stateless server; state as explicit handles
  • Budget live-environment verification

The long version, with commit-level citations: mcp-design-talk.md in this repo.

The take-home card. Ten lines, each one earned by a specific commit somewhere in the ecosystem, and each expanded with citations in the research document. If someone asks "which three matter most," my answer: test your docstrings against the live service, bound every output, and never let the server hold a standing credential.
