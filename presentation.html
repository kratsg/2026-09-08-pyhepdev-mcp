The talk in one line

Design the interface for the model; design the architecture for the credential. The top row is the easy part.

Start with the three-box diagram every MCP tutorial draws, because it's true: agent, server, backend, and the SDK makes that a weekend of work. Then reveal the second row: this is the same tool call as it actually runs in production. The user authenticated through Keycloak, the agent holds a personal access token, the gateway authenticates and authorizes once, a broker mints a short-lived identity token for exactly one backend, the backend redeems it for a real grid credential from a custodial service, and only then does Rucio hear about it. Every box in that second row exists because something broke without it. That's the talk: the interface work points at the model, the architecture work points at the credential.

Thirty seconds of scale-setting, no code. Six MCP-layer projects across five very different domains: data management, metadata, notebooks, filesystems, and one bridge that exists only to translate authentication. Four credential services that are deliberately not MCPs. One platform fronting all of it, deployed for the ATLAS Analysis Facility's user base. The footnote is a design point, not an apology: when I took this snapshot, the OpenSearch backend was down, and its fourteen tools were simply absent from the tool list instead of failing at call time. Failure isolation shows up in the tool surface itself.

An existing API is not an agent interface

What AMI returns

  • 100+ metadata fields per dataset
  • a 14-column tag table, most of it noise
  • duplicate rows, raw unit conventions
  • and mocked tests said all of this was fine

What the model gets

  • a 15-field allowlist, chosen by an analyst
  • the tag table pivoted to Level | Tags
  • deduplicated, units converted visibly (nb → pb)
  • every result ends with Next actions

And the prose is part of the API

The model reproduces docstring examples verbatim: one release needed four same-day commits fixing query syntax in documentation. Doc bugs are behavior bugs; nothing lints prose against schema yet.

ami-mcp commit 901f339 "optimize MCP tools for LLM usefulness"; doc fixes 74e9063, 000160c, 78a2ce3, 8bea8de.
This is the first lesson chronologically. ami-mcp wraps a twenty-year-old metadata service. The naive wrapper worked, passed its mocked tests, and was unusable: a hundred fields, a fourteen-column tag table, duplicates. One commit, titled "optimize MCP tools for LLM usefulness," is basically a catalogue of raw-wrapper failure modes and their fixes: allowlist, pivot, dedup. And it found a real parsing bug the mocks had hidden, because the real CVMFS files use double tabs. Second half: AMI is the one server where we teach the model a query language instead of wrapping every command. That makes the documentation executable, and it had to be debugged like code, against the live service. Four same-day commits fixed syntax errors in docstrings.

Errors are the agent's control flow

rucio-mcp tools/_helpers.py:116–212, abridged

  • Returned, not raised: a traceback is a dead end; prose the model reads is a transition edge
  • Names the next tool: most failures self-heal inside the agent loop
  • Empty results route too: "no replicas found; if it's a container, use…"
  • The taxonomy is the metrics: TOOL_ERRORS{category}, so agent confusion is dashboardable

Honest gap

None of this sets the spec's isError flag, and the platform once audited failing calls as successes. Do both.

Principle one of five. The consumer of an MCP is a probabilistic programmer: it course-corrects from prose, so an error message is not diagnostics, it's the next instruction. Three things to copy: return errors as normal results instead of raising, name the specific next tool in the recovery line, and give empty results a route too, because an empty result is the most common silent failure. And feed the same category taxonomy into your metrics: our Grafana can show which confusions agents actually hit. The honest gap: we return errors as plain text without the protocol's isError flag, and that bit us at the platform layer, where failing calls were audited as successes until we fixed it. Keep the recovery prose, and also set the flag.

Context is a bounded resource

War story: pagination theater

Five tools returned a tidy 100-row page while materializing the full result upstream: a 500k-file container was downloaded to serve one page. The output protected the model; nothing protected the server.

Fixed with streaming iterators by an external contributor, rucio-mcp 24f7497.

Every cap has three legs

  • Enforced server-side (the leg that drifts, so test it)
  • Announced in-band: Pass `offset=50` to see more.
  • Recoverable: "narrow path and retry" beats a bigger cap

Filesystem worst case is a known number: 1 MiB read · 200 matches · 10 s timeout · 4 concurrent ops per user.

At the platform layer

The gateway does not forward backend instructions (one server ships 10.5 KB of them): it composes its own 2–3 KB policy preamble, and filters the 110-tool list per user. Curation, not compression.

Principle two: treat the context window as a metered resource with a budget, the way you treat memory. The war story: five of our tools looked perfectly paginated from the model's side while materializing everything upstream; a half-million-file container got downloaded to serve one page. An external contributor caught it. Lazy end to end or it doesn't count. The rule I'd put on a poster: every cap needs three legs. It has to be enforced server side, it has to announce itself in the output so truncation never silently distorts the model's world view, and it has to come with a recovery move. The one leg that rots is enforcement; we found a documented grep cap that was never actually clamped, so test the clamps. And the same principle recurses at the platform: don't forward every backend's instructions; own that channel and keep it small, and trim the tool list per user.

Identity is ambient, never an argument

    ... create_notebook(owner=claims.unixname, ...)

af-jupyterlab-mcp tools/jupyterlab.py:48–66, abridged

  • No tool takes a username. The schema physically cannot express "read bob's files"
  • One rule, independent mechanisms: k8s owner labels · kernel uid/gid subprocesses · VOMS nickname from the redeemed proxy
  • Authority is resolved live from the directory, never from token claims: removing a group is a real kill switch

The principle

Make the dangerous parameter unrepresentable, not documented. An LLM argument is hallucinatable; a verified claim is not.

Principle three. Every agent-facing schema in the fleet has the same absence: there is no owner or username parameter anywhere. The user is whoever the verified token says, full stop. What makes this a real pattern rather than a slogan is that five servers implement it with completely different mechanisms: Kubernetes owner labels for notebooks, an actual setuid subprocess for the filesystem so the kernel is the enforcement, and the VOMS nickname inside the redeemed proxy for Rucio and AMI. And one platform-level sharpening: even the token doesn't carry authority. Groups and permissions are resolved live from the identity directory on every call, never read from token claims, so removing someone from a group takes effect in seconds, not at token expiry.

Keep credentials out of the MCP

Lifetime == one call

Redeem → 0600 temp file → one backend call → delete, success or failure. The server holds no standing secret; a test asserts the file is gone.

Exchange, never forward

The client's token never goes downstream (a spec MUST). Each hop re-mints: identity token in, aud= exactly one service, 600 s, no authorization claims.

Custodians per secret

Globus passphrase, CERN password, Condor pool key: each lives in its own tiny service, network-fenced to one caller, at its own privilege floor.

"Authorization model: none beyond identity, by design. … Do not add capability logic here based on token claims." the same module docstring in all three token services (krb5 app.py:1–10); authorize once, upstream

Why not in the MCP?

An MCP needs credentials to do its job; that does not make it the place to mint or store them. Blast radius of a compromised MCP: the in-flight tokens of currently active users, and nothing else.

Principle four, and the architectural heart. Three moves. First, credential lifetime equals tool-call lifetime: the MCP redeems a credential for this caller, uses it for exactly one backend operation, and deletes it on the way out; we test the deletion, not just the redeem. Second, exchange instead of passing through: the platform never forwards the client's token, which the MCP spec itself forbids. We even rejected the SDK's convenience proxy class because its default forwards headers. What goes downstream is a broker-minted identity token good for one audience for ten minutes, and heavy material like proxy PEMs never transits the gateway at all: the backend redeems it directly from the broker. Third, the root secrets. The pool password can mint tokens for anyone; the Globus passphrase unlocks the user's grid identity. Each lives in its own tiny custodial service whose docstring literally forbids adding authorization logic. Authorize once, at the broker; custodians verify who is calling and nothing else. Each service is a one-question security audit.

The environment is the hard part

A bridge you shouldn't need

CERN's OpenSearch MCP sits behind an Apache SPNEGO-only gate; our world speaks broker JWTs. The fix is a ~600-line adapter with zero MCP awareness:

  • verify the JWT, redeem a throwaway Kerberos ccache
  • shell out to curl --negotiate: Kerberos in zero lines of Python
  • ccache deleted per request; a test asserts it's gone

Can't modify the server (not ours), won't modify the client (blast radius): adapt the boundary, keep it protocol-blind.

After green CI: six straight production failures

  1. dependency packaging (db357eb)
  2. no krb5.conf in the container (e3140cd)
  3. CERN Grid CA missing from the Mozilla bundle (5eedad1)
  4. NetworkPolicy silently blocking KDC port 88 (bf3b62a)
  5. reverse-DNS SPN mismatch (05d2b2a)
  6. gzip body forwarded without Content-Encoding (a01bae9)

All environment, none logic.

The principle

Green CI cannot reach credential plumbing. Budget live-environment verification as first-class work, and treat the deployment manifest as part of the security design.

Principle five. One backend we genuinely could not change: CERN's OpenSearch MCP only speaks SPNEGO, negotiated Kerberos at the Apache layer. The answer was a deliberately dumb adapter: it translates authentication and nothing else, no JSON-RPC parsing, no policy, no standing secret. The entire Kerberos implementation is an environment variable and curl's GSSAPI. The right half is the real lesson. This service had full test coverage and green CI, and then failed six times in a row in production, once per layer of the environment: packaging, kerberos config, CA trust, network policy, reverse DNS, and a lossy header. Not one was a logic bug. The same story repeats across the credential services: secret mounts whose permissions the native binary refused, a chart whose own default network policy blocked its own default JWKS URL. Mocks can't reach any of that. Plan for it.

What breaks at ten MCPs (that one MCP never sees)

  • Silent shadowing: same-name tools resolve by registration order, so everything gets a prefix, and af_ is reserved for the gateway's own diagnostics
  • The registry is a contract: the service name doubled as the token audience; one governance rename 401'd the entire fleet
  • List-time credentials: a backend that needs auth just to list tools is invisible until the gateway minted best-effort list-time credentials
  • Version skew is standing: a new upstream tool ships disabled until an operator maps it to a permission (opt-in, per tool)
  • A permission matrix, not a flag: 12 permissions × 8 services × 124 tools; the portal grew a matrix page because nobody can hold it in their head
  • Failure isolation needs a taxonomy: not-linked / unauthorized / unavailable, and a dead backend vanishes from tools/list instead of failing calls

The platform bar

The Nth MCP must be config, not code: a services.yaml entry, a NetworkPolicy port, a permission mapping. And the platform can't fix tool quality centrally: it forwards descriptions verbatim, so it publishes authoring conventions and models them with its own tools.

af-mcp-platform issues #113, #257, #121; 289 commits, 77 days, 1,337 tests.
Everything so far was about one server at a time. At ten, a different class of problem appears, and none of it is in the MCP spec. Quick tour: naming, because two backends will eventually serve the same tool name and the failure is silent shadowing, not an error. Identity of a service versus its wire contract: our worst outage was a rename, because the registry name doubled as the token audience; they're separate fields now with a do-not-change comment. List-time credentials: rucio needs auth just to enumerate tools, which made it invisible to aggregation. Version skew: backends deploy independently, so new tools are disabled until reviewed. And failure isolation: when OpenSearch is down, its tools simply aren't in the list. The bar we hold ourselves to: adding the tenth service is configuration, not code. That's the payoff of the whole architecture.

One tool call, end to end · "check the replicas of DID X"

1

Claude calls rucio-atlas_rucio_list_dataset_replicas with its personal access token (minted once via OAuth + Keycloak; a PAT can never mint PATs)

2

Broker authenticates: hash lookup, revocation ≤30 s; groups and POSIX identity resolved live from the directory, never from token claims

3

Authorized once: this tool requires read_data; group permissions ∩ PAT grant; denials are audited too

4

Broker mints an identity token: sub=user, aud=rucio-mcp-atlas only, 600 s, no authorization claims; the PAT is never forwarded

5

rucio-mcp verifies it against the broker's JWKS, then calls back /v1/credentials/x509/redeem: the VOMS proxy goes broker → backend directly, never through the gateway

6

One Rucio call as the user; proxy file deleted; one audit record with trace id, token id, and grid nickname, plus metering and Prometheus

Three invariants: the inbound token is never forwarded · heavy credentials never transit the middle · every call is audited, including the denied ones.

This is the platform in one call, and it's the slide to slow down on. Walk the six steps. The thing to notice is how many different tokens exist: the personal access token the client holds, the ten-minute identity token the broker mints for exactly one backend, and the VOMS proxy the backend redeems directly from the broker. Each hop exchanges rather than forwards, which is exactly what the MCP spec's authorization section demands, and the proxy PEM never passes through the aggregator at all. Also notice what the identity token does not contain: any authorization claims. The docstring in the broker says if a backend is ever written to test token.permissions, the design has failed. Authority lives in one place. And the audit spine: exactly one record per call, success, failure, or denial, joinable to the client's trace and the usage accounting by one id.

Generalizes: keep

  • the broker spine; per-call credentials; one authorization brain
  • custodial services around every legacy credential (X.509/VOMS, krb5, IDTokens)
  • config-only admission of the Nth MCP

Change for a federation

  • structured outputs (outputSchema) and read-only/destructive annotations from day one
  • trust between site brokers (WLCG/SciTokens profiles): today's design is single-facility
  • real per-call consent for destructive ops, stronger than instructions
Honesty slide: what's transplantable and what's local. The layered shape generalizes: agents on top, one gateway that owns identity, authorization, and audit, domain MCPs that stay stateless and curated, and custodial services wrapped around every legacy credential system HEP has accumulated. That maps onto any facility. What I'd change if starting fresh or federating: structured outputs and tool annotations from day one, because we bet on markdown-only and paid for it at the platform layer, twice, measurably. Federated trust between site brokers doesn't exist yet; that's where WLCG token profiles slot in. And consent for destructive operations is currently permissions plus instructions to the model; a federation needs something a hostile model can't ignore. What's purely local: kernel-uid enforcement assumes POSIX and shared filesystems, and a surprising amount of the credential subsystem exists because of specific CERN constraints. Transplant the shape, not the code.

If you build an MCP tomorrow

  • One domain, stated non-goals; exposure strategy matched to the backend's shape
  • Descriptions written for the model and tested against the live service
  • Every output bounded; truncation announced in-band with a recovery move
  • Errors name the next tool, and set isError
  • No username parameters, anywhere
  • No standing credentials: redeem per call, delete on the way out
  • Authorize once, upstream; custodians refuse policy in writing
  • Budget live-environment verification: green CI can't reach the layer that fails
