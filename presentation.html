One minute of level-setting, since this is an introduction for scientific software developers. The Model Context Protocol is an open protocol, originally from Anthropic, now with a public spec and SDKs everywhere. The assistant, whatever it is, Claude, Gemini CLI, an editor, speaks MCP, which is JSON-RPC under the hood, to a server you write. That server can run on your laptop or be hosted at a facility, and it talks to whatever you already have however it wants: Python calls into rucio.client or pyAMI, a subprocess, a REST API. Three primitives, and honestly tools are the one that matters in practice: typed functions the model can call, described by a name, a schema, and a docstring. The pitch to this room: this is not prompt engineering and not training a custom model. It's ordinary interface design for an unusual caller. If you can write a Python API, you can write one of these; there's a minimal example below if we want it.

Around an existing Python project · backup

from fastmcp import FastMCP
from rucio.client import Client

mcp = FastMCP("rucio")
client = Client()

@mcp.tool()
def list_dids(scope: str,
              pattern: str = "*") -> str:
    """Search datasets in a scope by wildcard.

    Use a narrow pattern; results are paginated.
    """
    return ", ".join(
        client.list_dids(scope, {"name": pattern}))

mcp.run()

rucio-mcp started from this barebones structure

  • Everything the LLM sees is right here: name list_dids, schema scope: str, pattern: str = "*", description = the docstring
  • Wrap rucio.client, not the CLI: structured data in, curated text out
  • Start on stdio on your laptop; add HTTP when a facility hosts it
  • fastmcp handles the JSON-RPC; you only write the function
Backup, for the "how do I start" question. This is the barebones structure rucio-mcp started from: FastMCP, the native Rucio client, one decorated function. The decorator turns the signature into the JSON schema and the docstring into the description. Point at the left and the right together: the name, the two typed parameters, and that docstring are literally everything the LLM knows about this tool, which is why the docstring is API surface. Two pieces of advice if you do this tomorrow: wrap the client library, not the command-line tool, because you want structured data on your side of the boundary; and start with stdio on your laptop, where credentials come from your environment like they do for any script. Hosting it for other people is where the rest of this talk begins.

The point

The limiting factor is rarely the model. It's reliable, secure access to what scientists already use.

Start with the three-box diagram every MCP tutorial draws, because it's true: agent, server, backend, and the SDK makes that a weekend of work. Then reveal the second row: this is the same tool call as it actually runs in production. The user authenticated through Keycloak, the agent holds a personal access token, the gateway authenticates and authorizes once, a broker mints a short-lived identity token for exactly one backend, the backend redeems it for a real grid credential from a custodial service, and only then does Rucio hear about it. Every box in that second row exists because something broke without it. That's the talk in one line: design the interface for the model, design the architecture for the credential.

This is the first lesson chronologically, shown as bad versus good. ami-mcp wraps a twenty-year-old metadata service. The naive wrapper worked and passed its mocked tests, and the output was unusable: a hundred raw fields per dataset, cross-sections in nanobarn with no hint, duplicate rows, multiplied by every dataset in the answer. The fix commit is literally titled "optimize MCP tools for LLM usefulness": pick the fifteen fields an analyst would pick, convert units visibly so the model can't silently mix nb and pb, deduplicate, and end every result with named follow-up tools so the model knows where to go next. And the callout: the docstrings keep getting fixed against the tools' real behavior. AMI is the one server where we teach the model a query language, so the documentation is executable; when a documented example was wrong, the model reproduced the wrong syntax verbatim, and we fixed the docs the way you fix code, against the live service.

Empty results carry the same routing hints. The error categories also feed our monitoring, so we can see which tools confuse the agent.

MCP results have an isError flag so clients can tell failure from success. We didn't set it at first; do both.

The classifier behind the right panel: rucio-mcp tools/_helpers.py (classify_error).
The consumer of an MCP is probabilistic: it course-corrects from what it reads, so an error message is not diagnostics, it's the next instruction. Left panel: the default, a raw exception. Best case the agent guesses; worst case it retries the same call. Right panel: what rucio-mcp returns for the same failure. The error comes back to the agent as a normal result rather than being raised into the server logs, and the recovery line names the exact next tool, so most failures heal themselves inside the loop. Empty results, which are the most common silent failure, get the same treatment. Two housekeeping notes: the same error categories feed our monitoring, so we can literally chart which tools confuse the agent; and MCP has a flag on results, isError, that lets clients and gateways distinguish failure from success. We skipped it at first and our audit log counted failing calls as successes for a while. Return the friendly prose AND set the flag.

Context is a bounded resource

Pagination storm

Five tools returned a tidy 100-row page while downloading everything upstream first: one 500k-file container, fetched to serve a single page.

Paginate the upstream iterator too, not just the output.

Every limit, three parts

  • Enforced server-side: fs_read ≤ 1 MiB, fs_grep ≤ 200 matches
  • Announced in the output: Showing 50 results. Pass `offset=50` to see more.
  • Recoverable: "narrow path and retry"

At the platform layer

The gateway curates too: it writes its own short instructions instead of forwarding every server's, and only lists the tools you're allowed to call.

Treat the context window as a metered resource, the way you treat memory. The war story: five of our tools looked perfectly paginated from the model's side while downloading everything upstream first; a half-million-file container got fetched to serve one page. Paginate the upstream iterator too, or the pagination only protects the model and not the server. The rule I'd put on a poster: every limit has three parts. It's enforced server side, with a concrete number, like one megabyte per read and two hundred grep matches. It announces itself in the output, like the pagination footer on the slide, so truncation never silently distorts what the model believes. And it comes with a recovery move: narrow the path and retry, rather than asking for a bigger limit. And the same principle recurses at the platform: the gateway writes its own short instructions instead of forwarding every backend's, and only lists tools you're actually allowed to call.

Identity is ambient, never an argument

  • No tool takes a username. The schema cannot express "read bob's files"
  • One rule, different ways to implement, e.g.: k8s owner labels · kernel uid/gid · the VOMS nickname in your proxy
  • Who you are comes from the identity provider (Keycloak) on every call, not from what a token claims

The principle

Do not expose dangerous parameters; derive them from verified identity.

af-jupyterlab-mcp tools/jupyterlab.py, abridged.
Every agent-facing schema in the fleet has the same absence: there is no owner or username parameter anywhere. The user is whoever the verified token says, full stop. An LLM argument can be hallucinated or injected; a verified claim can't. One rule, implemented differently per backend: Kubernetes owner labels for notebooks, an actual setuid subprocess for the filesystem so the kernel does the enforcement, and the VOMS nickname inside your redeemed grid proxy for Rucio and AMI. And one sharpening: even the token doesn't carry authority. Who you are, your groups and your unix identity, is looked up from the identity provider, Keycloak in our case, on every call, rather than trusted from token contents. That's what makes removing someone from a group take effect in seconds instead of whenever their token expires.

Keep credentials out of the MCP

Lifetime == one call

e.g. a VOMS proxy or Kerberos ticket: fetch it → 0600 temp file → one backend call → delete it. The MCP server keeps nothing.

Exchange, never forward

The user's token never goes downstream (the spec forbids it). Each hop gets a fresh short-lived JWT, valid for one service, expiring in 10 minutes.

One service per secret

e.g. only condor-token-service touches the Condor pool key; the broker is its only allowed caller, and it returns short-lived IDTokens.

"Authorization model: none beyond identity, by design. … Do not add capability logic here based on token claims." the same module docstring in all three token services (krb5 app.py); permissions are decided once, at the gateway

Never store secrets in the MCP server. Keep them in a vault (OpenBao, here) behind the broker, and mint short-lived credentials per call.

The architectural heart, and the abstract's promise: authentication without exposing user credentials. Three moves. First, credential lifetime equals tool-call lifetime: when rucio-mcp needs your grid proxy, it fetches it, writes a mode-0600 temp file, makes exactly one backend call, and deletes it, success or failure. We test the deletion, not just the fetch. Second, exchange instead of forwarding: the user's own token never goes downstream, which the MCP spec explicitly forbids. What goes downstream instead is a fresh JWT the broker mints, valid for exactly one service and expiring in ten minutes. Heavy material like proxy files never passes through the gateway at all; the backend fetches it directly from the broker. Third, the root secrets. The Condor pool key can mint a token for any identity, so exactly one tiny service touches it, the broker is the only thing allowed to call that service, and its docstring literally forbids adding permission logic there. Permissions are decided once, at the gateway. Everything secret lives in a vault, OpenBao for us, never in an MCP server. Deep-dive below if credential plumbing is your thing.

The custodians · deep-dive

voms-token-service

The only pod that sees home dirs and Globus passphrases. Runs voms-proxy-init impersonated; privilege floor found live, five times.

krb5-token-service

Password → kinit → ticket; zero secrets at rest, passwords zeroed on every exit path. Rate limiter protects CERN's lockout counter, not itself.

condor-token-service

Runs condor_token_create next to the pool key, which "must never reach the broker": it can mint any identity.

Why three services, not one

Different privilege floors (root+caps / none / one init container). Merging them forces the union of privileges onto everything. Each is a one-question audit: "did this call come from the broker?"

Orchestrate the hardened native binary; parse artifacts (ccache bytes, PEM), never CLI prose.
Deep-dive for questions. Three services because three root secrets with three different privilege needs. voms needs root plus capabilities to read user keys, and every one of those facts was discovered in production: grid tooling checks file ownership, not just mode. krb5 needs no privileges at all and holds nothing; its rate limiter exists to protect CERN's account-lockout counter, a third party, which is my favorite example of consequence-driven design. condor sits next to the symmetric pool key that can mint tokens for any identity, which is exactly why it must never reach the broker's trust domain. Common thread: all three shell out to the battle-tested native binary and parse artifacts, ccache bytes and PEM, never the human-readable CLI output, which turned out to be locale-dependent.

What actually broke

Never the code. With tests green, production failed on:

  • Kerberos and CA trust config inside the container
  • network policy and DNS between the pod and the KDC
  • a proxy header quietly dropped in transit

The principle

Unit tests with mocks can't see any of this. Test against the real facility services before calling it done.

atlas-search-mcp-bridge · SPNEGO = negotiated Kerberos auth at the HTTP layer.
By "the environment" I mean everything between your code and the backend: containers, trust stores, network policy, DNS, the facility itself. One backend we genuinely could not change: CERN's OpenSearch MCP only accepts SPNEGO, negotiated Kerberos at the Apache layer, while everything on our side speaks OIDC bearer tokens. The answer is the diagram: a six-hundred line bridge that verifies the broker's token, uses the af-credentials library to drop a throwaway Kerberos ccache for that one request, and then lets curl's GSSAPI do the actual SPNEGO exchange. Zero lines of Kerberos in our Python, no policy, no standing secret, and it never parses the MCP traffic passing through it. The right box is the honest part: this service had full test coverage, and production still failed repeatedly, on Kerberos config and CA bundles inside the container, on a network policy silently blocking the KDC, on reverse DNS, and on a dropped header. Never the code. Mocked unit tests cannot see any of that, so budget real time for testing against the live facility services.

What breaks at ten MCPs (that one never sees)

  • Name collisions: two MCPs serve a tool with the same name; fix = a prefix per service (rucio-atlas_*, fs_*)
  • Each service gets its own fixed OAuth audience, pinned in config, never derived from a name that can change
  • Listing needs credentials too: some MCPs require auth even for tools/list, so the gateway mints one just to enumerate
  • New tools are opt-in: when an MCP releases a tool, it stays disabled until an operator maps it at the broker
  • Authorization is plain RBAC: Keycloak group → permission → tool
  • A dead backend disappears from tools/list instead of every call failing

Adding the Nth MCP

Each MCP is added via config (Infrastructure-as-Code). Sometimes it needs a token service, sometimes a bridge — never changes to the MCP itself.

af-mcp-platform issues #113, #257, #121. ↓ more scars
Everything so far was about one server at a time. At ten, a different class of problem appears, and none of it is in the MCP spec. Quick tour: name collisions, because two backends will eventually serve a tool with the same name and the failure is silent, so every service gets a prefix. OAuth audiences: each service's audience is pinned in config; we learned the hard way not to derive it from a display name, because a rename broke authentication for everything at once. Listing: some MCPs need auth just to enumerate their tools, so the gateway mints a credential for the listing itself. New tools are opt-in: when a backend ships a new tool, it stays disabled until an operator maps it to a permission at the broker. Authorization itself is nothing exotic, plain RBAC from Keycloak groups. And when a backend dies, its tools leave the list rather than erroring one call at a time. The payoff: adding the Nth MCP is configuration, infrastructure-as-code. Sometimes it needs a token service, sometimes a bridge, but you never modify the MCP itself.

The thing to notice is how many different tokens exist: the personal access token the client holds, the ten-minute JWT the broker mints for exactly one backend, and the VOMS proxy the backend redeems directly from the broker's vault. Interfaces that travel

Across LLM providers

  • Design for the least-capable LLM client: e.g. Claude Desktop had no OAuth discovery, so we added personal access tokens; gemini-cli choked on an OAuth metadata fallback, so we deleted it
  • Standard OAuth, standard transports, no provider-specific hooks

Across experiments

  • rucio-mcp already serves ATLAS, CMS, DUNE, ESCAPE: the domain layer is VO-agnostic
  • Transplant the shape (broker + custodians + config-only services), not the CERN-specific code

Interoperable tool interfaces are likely to matter more than model-specific integrations.

↓ how our choices scored against the evolving MCP spec
The abstract's closing claim, made concrete. Across providers: the discipline is designing for the least-capable client. We had a genuinely cleaner design for routing based on OAuth scopes, fully written up, and we shelved it because only one client on the market supports the feature; the write-up is committed next to the code. Same story with the OAuth metadata fallback we deleted after a different client choked on it. Standard auth, standard transports, nothing provider-specific: that's what "works across providers" costs. Across experiments: rucio-mcp is already multi-VO because Rucio is, and the whole facility shape, broker, custodians, config-only services, transplants to any lab. What doesn't transplant is the CERN-specific plumbing, and that's fine: it's all behind one provider interface and per-service config. If you take one sentence home, take the abstract's: interoperable tool interfaces will matter more than model-specific integrations.

When is an MCP server appropriate?

Build one when

  • a library or service scientists already use
  • assistants need it repeatedly, across clients
  • you want to control what context the agent gets injected with
  • you can bound outputs and make errors recoverable

Skip it when

  • a one-off script would do
  • the backend's API is still churning under you
  • the "tool" would hand the model a credential
Interoperable tool interfaces are likely to matter more than model-specific integrations.

Close on the abstract's promise: when is an MCP server appropriate. Build one when there's an existing library or service with real users, when assistants will need it more than once and from more than one client, and when you can actually bound the outputs and make the errors recoverable, because those are the two properties the model experiences directly. Skip it when a script would do, when the backend has no stable contract to wrap, or when the honest implementation would hand the model a credential; fix that boundary first. Then the two closing lines, slowly: interoperable tool interfaces will matter more than model-specific integrations. And the one I'd put on a sticky note: design the interface for the model, design the architecture for the credential. The checklist below is the hallway version; the full dossier with commit-level citations is mcp-design-talk.md in the slides repo.

The checklist · backup

  • One domain per server, with written non-goals: datasets, or metadata, or notebooks; not all three
  • Docstrings are the LLM's manual: write them for the model and test the examples against the live service
  • Bound every output with a hard server-side limit, and say in the output when you truncated
  • Errors name the next tool to call, and set MCP's isError flag on the result
  • Structured outputs (outputSchema) from day one, not retrofitted like ours
  • No username parameters: identity comes from the verified token, never from the model
  • No stored credentials in the server: fetch per call from a vault, use once, delete
  • Permissions decided at one gateway, not re-implemented per server
  • Stateless server: any state lives in the backend, addressed by an id the tools pass around
  • Test against the real facility: the failures live in config, trust stores, and network, not in your logic

The long version, with commit-level citations: mcp-design-talk.md.

The take-home card. Ten lines, each one earned by a specific commit somewhere in the ecosystem, and each expanded with citations in the research document, which is linked and public. If someone asks "which three matter most," my answer: test your docstrings against the live service, bound every output, and never let the server hold a standing credential.
